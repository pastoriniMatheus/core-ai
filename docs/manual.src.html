PONTO DE PARTIDAPor que diretrizes de agente falham

O erro não é escrever regras ruins. É escrever regras certas no mecanismo errado.

A forma usual de dar disciplina a um agente é um CLAUDE.md extenso mandando-o se comportar: sempre planeje antes, nunca instale bibliotecas desnecessárias, sempre rode os testes. Parece razoável e falha por três motivos estruturais.

1. O CLAUDE.md é cobrado em todo turno

Ele entra no prompt em cada turno de cada sessão. Um procedimento detalhado escrito ali é pago sempre para ser útil às vezes. Skills carregam sob demanda; hooks carregam nunca — executam. Escrever o procedimento dentro do arquivo sempre-carregado é pagar duas vezes pela mesma regra.

2. Instrução é probabilística

O modelo obedece quase sempre. "Quase" é exatamente onde moram os erros que chegam em produção.

Probabilístico · pode ser ignorado

"Nunca instale bibliotecas desnecessárias."

"Não peça permissão, apenas rode os testes."

"Sempre consulte o grafo antes de ler arquivos."

Determinístico · sempre executa

PreToolUse nega o comando de instalação e exige justificativa.

permissions.allow no settings.json — permissão é do harness, não do prompt.

PostToolUse roda o linter e devolve o erro ao agente.

A instrução "não peça permissão, apenas rode os testes" é o caso extremo: ela é inerte. Permissão é decidida pelo harness, nunca pelo prompt. A frase só ocupa tokens em todo turno, para sempre, sem efeito nenhum.

3. Duas autoridades de processo se anulam

Quando um conjunto de regras manda entrevistar o usuário até exaurir dúvidas e outro manda entregar o código e calar a boca, o agente oscila entre os dois. Ambas as regras são corretas — em momentos diferentes. Juntas no mesmo texto, elas destroem a assertividade que deveriam produzir.

A solução não é escolher uma. É separá-las em fases, para que nunca coexistam.

A escada, agora obrigatória

A regra "escreva o mínimo de código possível" vira uma parada real. Ao detectar npm install lodash, bundle add rails ou equivalente, o hook nega a chamada e devolve:

[core] Dependencia nova detectada: `npm install lodash`

A escada da preguica inteligente, antes de adicionar uma dependencia:
  1. YAGNI      - isso precisa existir agora?
  2. Repo       - ja existe algo no projeto que resolve?
  3. Stdlib     - a biblioteca padrao da linguagem resolve?
  4. Plataforma - um recurso nativo resolve?
  5. Instalado  - uma dependencia JA no projeto resolve?
  6. Uma linha  - da para escrever em uma linha?

Se a dependencia continuar sendo a resposta certa depois de subir a
escada, explique por que os degraus 1-6 nao resolvem e reexecute
prefixado com CORE_DEP_OK=1.

Não proíbe instalar — força justificar uma vez. A distinção que importa: npm install sozinho restaura o lockfile e passa; npm install lodash adiciona dependência e para.

O que o verificador por arquivo não alcança

Rust, Java, C# e Scala não entram na tabela acima — e isso não é esquecimento. Nessas linguagens o compilador precisa do projeto inteiro (crate, classpath, solution): não existe verificação de um arquivo isolado que seja confiável, e rodar cargo check a cada edição custaria minutos.

O buraco é fechado no outro extremo. stopVerify.projectCheck roda o build ou typecheck completo uma vez, no Stop, antes de a sessão encerrar:

{
  "stopVerify": {
    "projectCheck": ["cargo check"]        // ou "npx tsc --noEmit", "mvn -q compile"
  }
}

Barato por arquivo a cada edição; caro por projeto uma vez no fim. O custo é pago onde ele não atrapalha o fluxo.

Hook lento anula o ganho que deveria proteger. Por isso o escopo é o arquivo editado, nunca o projeto: timeout de 12 s e verificação de um arquivo só. Typecheck de projeto inteiro pertence ao Stop.

Provado, não presumido

Hook errado é pior que hook nenhum: bloqueia trabalho legítimo e o time desliga tudo na primeira semana. A suíte cobre os dois lados de cada regra.

Dois bugs que a suíte pegou

Saída perdida no Windows. O pre-bash-guard negava a chamada mas o motivo chegava vazio: process.stdout.write para um pipe é assíncrono, e o process.exit() seguinte descartava a saída. O stderr funcionava por ser síncrono, o que escondia o problema. Corrigido escrevendo direto no file descriptor com writeSync.

Ferramenta ausente bloqueando tudo. Com shell: true, um binário inexistente não produz ENOENT — o shell existe, executa e devolve erro comum, indistinguível de "o linter reprovou o arquivo". Numa máquina Windows sem rubocop, toda edição de .rb seria bloqueada. O exit code também não ajuda: o cmd.exe devolve 1 onde deveria devolver 9009. A correção foi checar a existência do binário antes de rodar, com where / command -v.

Os dois são falhas silenciosas: nenhuma produz erro visível, as duas tornariam o núcleo inutilizável. É a razão de a suíte existir.

CAMADA 1Contexto: o que o agente lê

O roteador de 40 linhas

O CLAUDE.md do núcleo não é um manual — é um roteador. Ele diz quem manda, qual fase e onde achar o resto. Alvo de 40 linhas; acima de 60, algo está na camada errada.

MecanismoQuando carregaServe para
CLAUDE.mdtodo turno, toda sessãoO mínimo indispensável: precedência e onde achar o resto
Skillsó quando relevanteO procedimento detalhado
Hooksó no eventoO que não pode depender do modelo lembrar

Grafo ou busca textual

A regra "nunca use busca textual, sempre consulte o grafo" é ativamente prejudicial: faz o agente rodar uma ferramenta pesada para achar um literal. A regra correta é condicional.

A pergunta é…FerramentaPor quê
onde está a string X?busca textualmais rápida e barata; o grafo não acrescenta nada
quem chama esta função?grafoé relação, não texto
o que quebra se eu mudar isto?graforaio de impacto é o que o grafo modela
quais arquivos têm este padrão?busca textualé uma pergunta lexical
qual o formato deste arquivo?leitura diretanão precisa de mapa

A armadilha do mapa velho. O pior erro de um grafo de código não é a ausência dele — é ter um desatualizado. O agente responde com alta confiança sobre uma estrutura que não existe mais, e não há sinal de erro: a resposta parece certa. O pre-bash-guard bloqueia consultas quando o grafo está muitos commits atrás do HEAD.

graphify-out/ nunca é versionado. É grande, muda a cada commit e produz conflito de merge garantido em qualquer equipe. É artefato regenerável, como node_modules.

CAMADA 2Processo: fases, não contradições

Os regimes incompatíveis deixam de brigar quando viram estados distintos.

EXPLORAR Descobrir onde o trabalho acontece grafo + subagente
saída: só a conclusão
modelo rápido
ALINHAR Eliminar ambiguidade antes de codar entrevista
saída: perguntas incisivas
modelo forte
IMPLEMENTAR Escrever o mínimo que resolve edição + testes
saída: mínima
modelo intermediário
PROVAR Mostrar que funciona suíte + revisão
saída: só o que falhou
modelo rápido

Cada fase fixa seu regime de ferramenta, verbosidade e modelo. Voltar é comum e saudável: descobriu na implementação que o requisito era ambíguo, volta para ALINHAR em vez de adivinhar.

Pule ALINHAR quando o pedido for pequeno e inequívoco. Entrevistar alguém sobre uma correção de typo destrói a confiança na ferramenta mais rápido do que qualquer bug. Regra sem exceção declarada é regra aplicada fora de contexto.

A skill mais valiosa é extrair-skill. Disciplina importada é genérica por construção: serve a qualquer projeto porque não sabe nada sobre o seu. O maior ganho de assertividade num projeto grande vem do oposto — do que só este time sabe. Qual comando de deploy mente sobre ter dado certo. Por que o caminho óbvio não funciona. Nenhuma ferramenta de prateleira traz isso; você extrai.

CAMADA 0 · ENTREGAO portão de publicação

Publicar não é o fim do trabalho — é o momento em que ele passa a existir para outras pessoas.

Uma PR aberta fica visível para o time inteiro sob o nome de quem a abriu. Um card movido para revisão puxa o tempo de alguém. São ações socialmente irreversíveis, e por isso têm portão — o portão é o usuário.

Regra zero: nunca abrir uma PR e nunca mover um card para revisão sem permissão explícita do usuário. Por PR e por card. Toda vez.

Não vale “está pronto e a CI está verde”. Não vale “está obviamente pronto”. Não vale “o card anterior desta mesma leva foi autorizado”. Autorização é por item: um sim para uma tarefa não é um sim para a próxima.

O que o hook verifica sozinho

O pre-publish-guard intercepta gh pr create, gh pr merge, glab mr create, force-push e chamadas ao tracker. Leitura passa livre: gh pr view, gh pr list e git push comum não são publicação.

[core] Portao de publicacao: `gh pr create --fill`

  [x] PROVA AUSENTE — codigo alterado e nenhum teste rodou depois:
     - src/billing.rb
     - src/invoice.rb

  Antes de abrir/alterar uma PR, confirme com o usuario. Por PR e por card, toda vez.
  O usuario nao falou desde a ultima edicao — ninguem autorizou esta publicacao.

  Antes de pedir a permissao, tenha:
    - o caminho REAL exercitado, nao so a suite unitaria
    - contraprova: o teste falha sem o fix e passa com ele
    - o que ficou de fora dito explicitamente
    - base da PR: `develop`

  Pare, relate o que foi verificado e o que segue aberto, e pergunte.
  Com a autorizacao em maos, reexecute prefixado com CORE_PUBLISH_OK=1

Duas coisas são verificadas de fato no transcript: se houve edição de código sem teste rodado depois (e quais arquivos), e se o usuário falou desde a última edição — porque se ninguém falou, ninguém autorizou. A autorização em si não é verificável com certeza, e é por isso que a barreira é obrigatória em vez de condicional.

O marcador CORE_PUBLISH_OK=1 significa “eu perguntei e o usuário disse sim”. Usá-lo sem ter perguntado é mentir para a única salvaguarda que existe.

Suíte verde não é “testado”

Antes de oferecer o trabalho como pronto, exercite a coisa real: a tela no navegador contra a stack, o endpoint contra um servidor de verdade, o fluxo de ponta a ponta. Se o ambiente para isso não existe, construa ou diga com essas palavras que não foi exercitado.

É o tipo de defeito que passa por todo teste unitário e aparece no primeiro uso — uma chave emitida que não podia ser recuperada, uma consulta pausada renderizando como “vazio”.

Os três movimentos do card

MovimentoQuem faz
pegar a tarefa / iniciaro agente, quando o trabalho começa de fato
mover para revisãoo agente, com permissão explícita, e só com a PR já criada e linkada no comentário
mover para concluídosomente quem revisa, à mão. Nunca o agente, nunca o autor
Bloqueio com escape

Abrir PR, mover para revisão, force-push.

O agente pergunta, o usuário autoriza, o comando segue com o marcador.

Bloqueio sem escape

Mover o card para o estado final.

Nem com autorização do usuário: fechar um card é o julgamento de quem revisou, e a autorização não transfere o julgamento.

O contrato do comentário

Quando a permissão vier e o card for movido, o comentário não é um aviso — é o que o revisor lê antes de olhar o código.

  • Link clicável da PR. URL inteira, nunca só #123: referência curta entre repositórios raramente vira link no tracker.
  • Os SHAs dos commits que a PR carrega.
  • O que foi exercitado, com o resultado — e o que não foi.
  • Referências cruzadas nomeando o tipo de dependência: não “relacionado a X”, mas “conflita textualmente com X”, “precisam entrar juntos”, “encontrado ao testar X”. Nos dois cards.

Uma história só em todos os artefatos. Descrição do card, comentário, corpo da PR e runbook contam a mesma coisa. Quando uma conclusão muda, ela muda nos quatro — deixar a recomendação nova no card e a velha no comentário é gafe, e o revisor encontra.

Configurar para o seu tracker

O núcleo não sabe qual tracker a equipe usa. Em .claude/core.json:

{
  "publish": {
    "trackerPatterns": ["tracker[.]suaempresa[.]com/api"],
    "reviewState": "In Review",
    "doneState": "Done",
    "baseBranch": "develop"

Sem trackerPatterns, o portão continua valendo para PRs — só não reconhece comandos de tracker.

CAMADA 3Onde o custo realmente está

Cortar linhas de código geradas é um ganho real. Mas não é onde está o dinheiro.

Os números abaixo são desta sessão — a que produziu este próprio núcleo, medidos por scripts/baseline.mjs nos transcripts locais.

Uma ferramenta que corta 20% do código gerado ataca a barra âmbar. A arquitetura de contexto ataca a barra teal. As duas somam — mas só uma delas muda a conta.

As duas alavancas reais

Subagente para busca ampla. Delegue toda busca cujo resultado útil é menor que o material lido. Procurar em quarenta arquivos para concluir "a validação mora em auth/rules" é o caso perfeito: o subagente lê os quarenta, você recebe uma frase — e os quarenta continuam fora do seu contexto em todos os turnos seguintes.

Modelo por tipo de tarefa. Rodar o modelo mais forte com esforço máximo em toda tarefa é o maior desperdício silencioso que existe. Buscar arquivo não exige raciocínio profundo.

TarefaPerfil

arquitetura, modelagem de domínio, bug sutilmodelo forte, esforço alto

Você não copia nada manualmente. Um script escreve tudo; a única escolha é o escopo.

O preço do global: as guardas valem mesmo — inclusive num repositório de terceiro que você só foi ler. Bloquear npm install em código que não é seu incomoda rápido.

A combinação que funciona: global uma vez, e depois por projeto naquele onde você trabalha de verdade. O segundo comando acrescenta o que só faz sentido por projeto e não duplica os hooks.

# 1. uma vez, para todos os projetos
node scripts/install.mjs --global

# 2. em cada projeto de verdade
node scripts/preflight.mjs ~/meu-projeto   # o que falta instalar
node scripts/install.mjs   ~/meu-projeto
node scripts/doctor.mjs    ~/meu-projeto   # confirma

# 3. dentro do Claude Code, no projeto
/core-setup

O instalador é aditivo: hooks de outras ferramentas no mesmo evento são preservados, uma skill sua com o mesmo nome não é sobrescrita, e rodar duas vezes não duplica nada.

OPERAÇÃOMedir antes de acreditar

# ANTES de mudar qualquer coisa
node scripts/baseline.mjs --days 7 --save antes

# depois de cada fase do rollout
node scripts/baseline.mjs --days 7 --compare antes

Instalar quatro ferramentas de uma vez e sentir que melhorou não é resultado — é viés de confirmação. Sem número de partida, uma regressão passa despercebida e ninguém sabe qual mudança causou o quê.

Como ler

  • Turnos por sessão é o melhor indicador de assertividade: menos ida e volta corrigindo rumo para o mesmo trabalho.
  • Não celebre queda de output isolada. Resposta mais curta sem queda de turnos pode ser só verbosidade menor, não acerto maior.
  • Cache lido é onde a economia de arquitetura aparece.

Não há tabela de preço embutida de propósito: preço muda e envelhece errado. O que compara antes e depois é a contagem por categoria.

ADOÇÃORollout faseado

Instalar tudo de uma vez é garantir que ninguém saiba qual mudança causou o quê.

  1. Semana 0 · risco zero

    Baseline e allowlist de permissões. Ganho puro de tempo, sem mudar nada no comportamento do agente. Se parar aqui, o time já sai no lucro.

  2. Semana 1 · risco baixo

    Camada 0. Os três hooks entram. É onde está a redução real de erro. Compare com o baseline no fim da semana.

  3. Semana 2 · risco baixo

    Grafo e roteador. Mapa de dependências com reconstrução automática, mais o CLAUDE.md enxuto e o CONTEXT.md começando a encher.

  4. Semana 3 · risco alto

    A autoridade de processo. A troca mais disruptiva: a que muda como as pessoas trabalham, não só o que a máquina faz. Ela vem por último de propósito, com o baseline das três semanas anteriores para comparar.

  5. Semana 4 · opcional

    Base de conhecimento externa. Fora do caminho crítico, sempre. Ferramenta não-oficial sobre API não documentada não pode ser fonte de verdade de uma equipe — o repositório é.

Autorização não transfere julgamento. Você pode autorizar o agente a publicar o trabalho; não pode autorizá-lo a ter revisado o trabalho. Fechar um card é o julgamento de quem revisou — por isso esse é o único bloqueio do núcleo sem escape, nos três caminhos: comando de shell, o script do próprio núcleo e chamada MCP.

Sete testes cobrem essa regra, incluindo o nome do estado em português — ele varia por projeto.

Graphify: local ou servidor

Local — padrão

O grafo vive em graphify-out/, fora do git, e o hook post-commit o reconstrói a cada commit.

Zero infra para manter. Cada pessoa tem o seu.

Servidor MCP

Um servidor só, o time consulta por MCP.

Compensa quando o build fica lento num repositório grande — ao custo de mais uma peça para manter, e de alguém precisar reconstruir o grafo a cada push, senão o servidor serve um mapa velho para todo mundo de uma vez.

A configuração do modo servidor é escrita mesmo antes de o servidor existir, com a URL por preencher: quando ele subir, troca-se a URL e nada mais muda no projeto. Decidir por servidor antes de ter medido o tempo de build é criar manutenção para um problema hipotético.

O grafo é construído com --code-only: parsing local por tree-sitter, nada sai da máquina. Sem esse flag, documentos e PDFs do repositório vão para o LLM configurado — num projeto com contrato de cliente, é a diferença entre local e vazamento.

O que não entra

mattpocock/skills. Quando essa escolha foi feita, o núcleo não tinha skills próprias. Hoje fase faz o alinhamento, atacar-card conduz a implementação e entregar-trabalho fecha a entrega — as três escritas a partir das skills do próprio time. Instalar por cima criaria duas autoridades de processo disputando cada decisão, que é o erro que este núcleo existe para eliminar.

Obsidian. O CONTEXT.md e os docs/ já fazem o papel de conhecimento versionado, e um vault separado seria mais uma coisa a manter em sincronia — vivendo fora do repositório, que é onde decidimos que mora a verdade da equipe. Quem quiser o grafo navegável tem graphify . --obsidian: um flag, não uma ferramenta a mais.

Atualizar o núcleo

claude plugin update compara só a versão declarada. Um repositório com skills novas e a mesma versão faz o comando responder “já está na última” — e o time fica com o cache antigo, sem erro visível, porque a mensagem de sucesso é idêntica à de quando não há o que atualizar.

claude plugin marketplace update agent-core
claude plugin update core@agent-core

São dois comandos: atualizar o marketplace não atualiza o plugin.

PROVAValidado em sessão real

Uma suíte verde prova que o simulador funciona. O que prova o sistema é ele bloqueando trabalho de verdade.

Os hooks foram carregados numa sessão real do Claude Code, dentro de um projeto Go criado para isso — um gerenciador de fila de espera de restaurante, com go.mod, testes e histórico git. Três cenários, três sessões independentes.

19/19 na aceitação automatizada. As cinco guardas disparam em sessão real do Claude Code, contadas no transcript — não deduzidas da resposta do agente. Um comando reproduz tudo: node scripts/aceitacao.mjs.

Rodar você mesmo

Toda essa validação virou um comando. Ele cria o projeto descartável, instala o núcleo, roda as quatro sessões e lê o veredito do transcript — não da resposta do agente.

node scripts/aceitacao.mjs            # completo, ~10 min
node scripts/aceitacao.mjs --offline  # instalação e guardas, segundos
node scripts/aceitacao.mjs --manter   # não apaga o projeto no fim

Não exige instalar nada: Node já vem com o Claude Code, e o projeto de teste é JavaScript puro com node --test. O diretório é temporário e some no fim — nada toca seus repositórios.

O que ainda não foi validado

  • Mac e Linux. O ramo Unix de binExiste nunca executou como código de hook.
  • O marketplace. Os hooks foram carregados por settings.json apontando caminhos absolutos; a distribuição via plugin GitHub não foi exercitada.
  • MCP em sessão real. Os 9 testes de MCP são sintéticos — nenhum servidor MCP de tracker foi acionado de verdade.
  • Codex, Antigravity e Cursor. As skills e o CLAUDE.md portam como AGENTS.md; os hooks e as permissões, não. Sem eles sobra instrução que o modelo obedece quase sempre — que é o que este núcleo existe para substituir.
  • Convivência com outros hooks registrados no mesmo evento.

Uma descoberta operacional: permissions.allow só vale depois de aceitar o diálogo de confiança do workspace. Antes disso o Claude Code ignora as 48 regras e avisa no terminal. Os hooks funcionam de qualquer forma — mas o ganho de tempo da allowlist exige abrir o projeto interativamente uma vez.

EXTENSÃOCamadas de projeto, sem misturar

Cada projeto ganha um plugin próprio em plugins/<nome>/, declarado no mesmo marketplace.json. O projeto habilita só o que precisa:

{
  "enabledPlugins": {
    "core@agent-core": true,
    "projeto-a@agent-core": true
  }
}

Um projeto que não habilita uma camada não enxerga as skills dela. O isolamento é por construção, não por disciplina — ninguém precisa lembrar de não misturar.

A fronteira

Se uma skill menciona um sistema específico pelo nome, ela não pertence ao núcleo. Núcleo é o que vale para qualquer projeto; camada é o que vale para um.
